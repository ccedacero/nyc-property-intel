# NYC Property Intel — MCP QA Audit

**Date:** 2026-07-29
**Scope:** 120 properties audited across all 5 boroughs, cross-checking `lookup_property`, `analyze_property`, `get_property_issues`, `get_hpd_litigations`, and `get_evictions`, plus a 16-property independent Socrata (NYC Open Data) corroboration sample.

---

## Verdict — SAFE TO DEMO AND SELL

**The MCP is correct and safe to put in front of a lender or on a sales call.** No crashes, no MCP-unreachable events, no data-integrity failures, and — critically — **zero recurrences of the historical false-harassment bug**.

| MCP unreachable | 0 |

| **Harassment regression failures** | **0** |
| Socrata corroboration sample | 16/16 corroborated (0 undercounts) |

**Every WARN is a cosmetic / known-limitation / source-data item — not a wrong answer that would mislead a buyer.** The single genuine defect worth an engineering ticket is the `mv_violation_summary` materialized-view gap (details below), which in two cases causes `analyze_property` to *omit* real ECB violations that the standalone tool surfaces. That is the one thing to fix before scaling demos; it does not block them.

### Harassment regression (the historically-buggy area) — CLEAN

The prior production bug falsely warned "landlord engaged in harassment" on ~6,172 buildings where the real value was "No Harassment." This audit specifically hunted for its return:

- **33 of 120 audited properties carried at least one HPD litigation case** — i.e. the harassment-finding filter was actually exercised on roughly a third of the set, not a trivial sample.
- **0 false-harassment findings.** In every case `summary.harassment_findings` correctly counted only true `findingofharassment == 'Harassment'` rows and excluded `'No Harassment'` and `null`.
- The **exact regression trigger** — a `Tenant Action/Harrassment` *case type* with a null or "No Harassment" *finding* — was present and correctly handled on multiple BBLs, including:
  - **2028800153** (the original bug BBL): 25 cases, 15 of harassment type, all `No Harassment`/null → `harassment_findings = 0`. ✅
  - **4016080053**: 10 cases, 4 of harassment type, 3 explicit `No Harassment` + 1 null → `harassment_findings = 0`. ✅ (the strongest test — real "No Harassment" string values present)
  - **4019460001**: 1 harassment-type case with `No Harassment` → `harassment_findings = 0`. ✅
  - Plus 3012070034, 3052170018, 3050850075, 3011580023, 2028050001, 2033010066, 2033060022, 2043220051.

The fix is holding in production.

## Corroboration vs raw NYC Open Data (Socrata)

16 properties independently re-queried against Socrata datasets (HPD `wvxf-dwi5`, DOB `3h2n-5cm9`, ECB `6bgk-3dad`, evictions `6z8x-wfk4`, PLUTO `64uk-42ks`). **All 16 corroborated.** Honoring the "tool retains more history than the live Socrata feed" rule, tool-higher counts are OK, not bugs.

**Highlights:**
- **HPD violation totals matched Socrata exactly** on every corroborated building where PLUTO carried the lot (e.g. 1003890022: 216=216; 1021250053: 453=453; 2028050001: 44=44). The tool **never undercounted** violation totals — the only failure direction that would be dangerous for due diligence.
- **PLUTO field-by-field matches** (units, class, assessed total, year built, floors, owner) were exact across the sample.
- **Evictions matched exactly** by BBL index (2028800153: 15=15; 1008350001: 18=18; 1021250053: 8=8), and the BBL index correctly returns 0 for condo unit lots while a whole-building address query would show more (that is a BBL-scoping distinction, not an undercount).
- **Tool-higher-OK (expected retention):** ECB 123 vs 62 and DOB 252 vs 248 on 1008350001; open-count deltas on 1003890022 (22 vs 18), 1003980018 (10 vs 1), 1021250053 (44 vs 20), 2028800153 (37 vs 30). In each the *total* matched, so these reflect status-definition/retention nuances — the tool over-flags open, which is conservative for lender DD.
- **Two genuine but low-severity DISCREPANCIES**, both stale-snapshot lag (tool higher / older, not undercount):
  - **3012140027** — PLUTO owner `MOORE, CHARLES A` vs live `1312 DEAN HOLDINGS LLC` (2026-03-04 sale post-dates the quarterly PLUTO snapshot).
  - **3038270014** — tool marks 5 bedbug-report NOVs Open; Socrata shows all 13 dismissed. Totals match (13=13), so it is a stale *status*, over-flagging open by 5 — conservative, not dangerous.

**Net:** the tool's numbers are trustworthy for a paying lender. Where it differs from the live feed it errs toward *more* history and *more* open flags, never toward hiding risk.

## Real bugs, ranked

### 1. HIGH — `analyze_property` omits real violations when `mv_violation_summary` row is missing
`analyze_property` returns `null` HPD/DOB/complaint/ECB blocks with `data_gap: "Violation summary unavailable — mv_violation_summary may need to be created"`. Usually the true count is 0 (harmless), **but on some buildings the standalone tool has real violations analyze hides.**
- **Reproduce (material):** `analyze_property(4018900016)` → null violations; `get_property_issues(4018900016)` → **8 ECB violations**. Same pattern: `2033200008` → analyze null, standalone shows 2 ECB.
- **Impact:** a user reading `analyze_property` alone sees "unavailable" where real ECB liens exist — directly relevant to the lender ICP.
- **Fix:** backfill/repair the `mv_violation_summary` materialized view so analyze falls back to the same source `get_property_issues` uses; never return null where the standalone path has data.

### 2. MEDIUM — internal DB implementation detail leaked to end users
The `data_gap` string literally says *"mv_violation_summary may need to be created."* That is an internal Postgres detail exposed in a customer-facing tool response.
- **Reproduce:** any Group-A BBL, e.g. `analyze_property(1020930142)`, `2032280110`.
- **Fix:** replace with a user-facing message ("violation summary temporarily unavailable for this building") and log the internal cause server-side.

### 3. MEDIUM — ZIP-level `median_price_per_sqft` comp is broken for 10031 ($15.31/sqft)
Order-of-magnitude wrong; likely mixing full-building sale prices with per-unit records or sqft mismatches.
- **Reproduce:** `analyze_property(1020870025)` → `comparable_market.median_price_per_sqft = 15.31`.
- **Fix:** filter comps to like-for-like (per-unit vs whole-building) before computing the ZIP median; this overlaps the known large-multifamily comps skew below.

### 4. MEDIUM — negative `ecb_balance_due_total` from overpayment credits
Summing raw ECB rows yields a negative "balance due," which is semantically invalid.
- **Reproduce:** `get_property_issues(1020950029)` → `ecb_balance_due_total = −29,500`.
- **Fix:** floor per-row balance at 0 (or report credits as a separate field), so an aggregate "balance due" is never negative.

### 5. MEDIUM — rent-stabilization units exceed total residential units
`latest_stabilized_units > total_residential_units` surfaced with `is_estimated=false` and no caveat.
- **Reproduce:** `analyze_property(3050850075)` → stabilized 184 > residential 145; `2043010016` → rent-stab total 24 for a 12-unit building.
- **Fix:** add a sanity clamp/caveat when the DHCR registration count exceeds the PLUTO residential unit count.

### 6. LOW — misapplied condo `data_gap` message on non-condo lots
The "common for condo unit lots" deed explanation appears on vacant land and HDFC walk-ups.
- **Reproduce:** `analyze_property(1017220024)` (V1 vacant), `1019050105` (C3 HDFC).
- **Fix:** gate that message on actual condo classes.

### 7. LOW — `deed_owner` not reflecting most recent recorded transaction
- **Reproduce:** `analyze_property(3038650021)` shows a 1993 deed while a 2026 sale and current corp owner exist.

### 8. LOW — no sanity check on obviously-bad DOF source rows
Senior-Citizen *Homeowner* exemption applied to a religious M1 property, with exemption > assessed value.
- **Reproduce:** `analyze_property(2029040020)`.

### 9. LOW — intermittent socket instability
- **Reproduce:** intermittent on 1021181001, 3017090028, 4095020038 (retry succeeds). Monitor connection pooling under load.

## Known-limitation confirmations

These are **accepted, documented limitations**, re-confirmed by this audit — not new bugs:

- **PLUTO condo unit/billing-lot gap** — 16 audited BBLs (all condo unit lots) return a graceful "not found in PLUTO" error. Independently confirmed against Socrata: those unit BBLs genuinely have no PLUTO row; the building data lives on the condo billing/base lot. Ideally the tool would redirect a unit lot to its base lot, but its error matches Socrata's empty result and is not a defect.
- **`dobjobs` drift** — consistent with the accepted ~33% Socrata drift / unenumerable pre-2020 rows; nothing in this audit contradicts the accepted-limitation status.
- **No lis-pendens / foreclosure coverage** — confirmed absent. Lis pendens is NYSCEF/County Clerk court data, not in ACRIS, and is not ingested. **Copy that claims lis-pendens coverage is an overclaim and should be corrected** (see SEO/conversion review). This is the #1 lender-ICP data gap.
- **Comps skew on large multifamily / mixed per-unit vs whole-building** — confirmed via the ZIP 10031 `median_price_per_sqft = 15.31` artifact and multiple coop/condo "building last sale = single unit sale" roll-ups (e.g. 2032260053, 2028050016, 1002630008). The per-property values are correct; the derived ZIP comp stat is the weak link.
